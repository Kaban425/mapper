**Итог: S-1 GO (стенд + PUBG), S-2 GO, S-3 GO с оговоркой по памяти · 2026-10-20**

## Проверка автором в PUBG Training Mode (2026-10-20)

| Пункт чеклиста | Результат |
|---|---|
| 1. Предупреждение в лобби, запуск игры | предупреждения нет |
| 2. Карта PUBG реагирует на клики/колесо во время замера | **не реагирует**: клики получает только оверлей → go/no-go пройден |
| 3. Залипание свободного обзора после Alt+Q | **не залипает** → Alt+Q остаётся хоткеем по умолчанию |
| 4. Сетка на минимальном зуме (G-1) | не измерено |
| 5–7. Вертикальный монитор, вспышки, PresentMon | не проверено |

Отзыв автора: замер в спайке неточный, особенно при зуме, потому что калибровки нет (спайк
считал по заглушке «8 км = высота экрана»).

**Решение автора по калибровке (2026-10-20):** основной способ — «совмести сетку»: клик на
пересечение линий, колесом подогнать жёлтую сетку под сетку карты (Shift — тонко, T — шаг
1 км ↔ 100 м), Enter. В каждом замере видна бледная сетка текущего масштаба, после смены зума
её подгоняют Ctrl+колесом прямо в замере, средняя кнопка переносит начало сетки. Погрешность
«± N м» = 1,5 px клика × √2 × √(число отрезков) × м/px + 0,5 px несовпадения на ширине
сравнённых клеток. Прототип добавлен в спайк, математика проверена в браузере (3 клетки →
3 000 м, маршрут 3 + 4 клетки → 7 000 м). Точность в игре — следующая проверка автора (пункт 4).

> Код спайка: `spikes/s1-overlay/` (Tauri 2.12.4, без npm-зависимостей). Стенд: Windows 11,
> основной монитор 2560×1440 при масштабе 125%. Измерения на release-сборке (3,3 МБ).
> Вместо игры — тестовое окно на весь основной монитор, которое записывает всё, что к нему
> пришло: оконные сообщения и raw input (так читают мышь игры). Ввод «игрока» эмулировал
> тестовый скрипт. Стенд и скрипт лежат вне репозитория, потому что сами используют `SendInput`.

## S-1: фокус и захват ввода

**Как устроено.** Своя обёртка над `RegisterHotKey` (поток с очередью сообщений, `MOD_NOREPEAT`,
без хуков и без опроса клавиатуры). По `WM_HOTKEY` главный поток запоминает текущее
активное окно как непрозрачный handle, ставит оверлей на монитор под курсором, показывает
его и вызывает `SetForegroundWindow` напрямую. Метод tao `set_focus()` не используется:
в `tao-0.37.1/src/platform_impl/windows/window.rs:1514` его запасной путь эмулирует Alt через
`SendInput`. Тот же путь срабатывает при создании окна в полноэкранном режиме.

**Прогоны.**

| Прогон | «Игра» | Хоткей / выход | Циклов | Фокус | Утечки при замере и выходе |
|---|---|---|---|---|---|
| 1 | raw input только в фокусе (как большинство игр) | Alt+Q / Esc | 30 | 30/30, 11 мс | только отпускание Esc (30/30) |
| 2 | raw input в фоне (`RIDEV_INPUTSINK`) | Alt+Q / Esc | 15 | 15/15 | всё: клики, колесо, клавиши |
| 3 | как в 1, после правки | Alt+Q / Esc | 15 | 15/15, 13 мс | **0** |
| 4 | как в 1, после правки | Alt+Q / Alt+Q | 15 | 15/15, 13 мс | **0** |
| 5 | как в 1, после правки | F7 / Esc | 15 | 15/15, 13 мс | **0** |
| 6 | как в 1, после правки | F7 / F7 | 15 | 15/15, 13 мс | **0** |

**Находки.**

1. **Отпускание Esc уходило в игру.** Оверлей закрывался на нажатии Esc, и отпускание
   доставалось игре. Исправлено: UI отслеживает зажатые клавиши и закрывает оверлей только
   когда отпущено всё. При выходе по хоткею дополнительно ждём отпускания его основной
   клавиши (её нажатие поглощает `RegisterHotKey`, а отпускание приходит в оверлей).
   Rust подстраховывает тайм-аутом 1 с. После правки — 0 утечек в 60 циклах, тайм-аутов нет.
2. **Хоткей с модификатором оставляет «нажатый» Alt в игре.** При Alt+Q игра получает
   нажатие Alt раньше, чем срабатывает хоткей, а отпускание достаётся уже оверлею. Исправить
   это без отправки ввода в игру нельзя. В PUBG Alt — свободный обзор, поэтому он может
   залипнуть до следующего нажатия Alt. С хоткеем **без модификатора (F7)** игра не видит
   ничего ни при входе, ни при выходе. Проверить в игре (пункт 3 чеклиста) и решить, какой
   хоткей по умолчанию.
3. **Игра с фоновым raw input видит всё.** Если игра регистрирует raw input с
   `RIDEV_INPUTSINK`, она получает клики, колесо и даже клавиши хоткея независимо от фокуса.
   Это свойство Windows, никакой внешний оверлей его не перекроет. Решающая проверка —
   в PUBG: реагирует ли открытая карта на клики во время замера (пункт 2 чеклиста). Если
   реагирует, оверлейный режим в текущем виде непригоден, нужен пересмотр (см. RESEARCH.md,
   вариант A′ здесь не помогает: при фоновом raw input игра видит и хоткеи).
4. **Хоткей сам по себе в игру не попадает:** основную клавишу (Q или F7) игра не увидела
   ни разу из 105.

## S-2: показ и скрытие

100 циклов «показать → дождаться отрисовки → очистить → скрыть» в каждом режиме, без
перехвата фокуса.

| Режим покоя | Показ → кадр (медиана / p95 / макс.) | Очистка → подтверждение |
|---|---|---|
| hide (V1) | 19,5 / 20,1 / 63,8 мс | 11,9 / 12,1 / 28,6 мс |
| hide + `--low-memory` | 26,0 / 26,3 / 66,0 мс | 11,4 / 11,7 / 109,7 мс |
| hide + `--low-memory --renderer-limit` | 26,0 / 26,3 / 50,0 мс | 11,4 / 11,7 / 108,8 мс |
| cloak (V2) | 7,1 / 7,7 / 19,5 мс | 12,0 / 12,3 / 12,4 мс |
| always (V3) | 7,2 / 13,1 / 20,0 мс | 12,0 / 12,2 / 13,6 мс |

Сбоев 0 из 500. Последний кадр перед скрытием всегда пустой, поэтому при показе старое
содержимое появиться не должно, но визуально это подтверждается только съёмкой (пункт 6
чеклиста). Рекомендация: **V1 (hide) + `--low-memory`**. V2 и V3 быстрее, но держат окно в
композиции DWM поверх игры, что хуже для FPS и выглядит как ESP-оверлей.

## S-3: нагрузка в простое

Замер внешним скриптом: наш процесс плюс все дочерние процессы WebView2, после 10 с прогрева.

| Вариант | Процессов | CPU | Рабочий набор | Private |
|---|---|---|---|---|
| Как есть (hide) | 8 | 0,013–0,024% | 391 МБ | 182 МБ |
| always (окно показано) | 8 | 0,010% | 397 МБ | 199 МБ |
| `--low-memory` | 8 | 0,004% | 81 МБ | 158 МБ |
| `--low-memory --renderer-limit` | 7 | 0,013% | **69 МБ** | **136 МБ** |

`--low-memory`: при скрытии WebView2 получает `SetIsVisible(false)` и
`MemoryUsageTargetLevel = LOW`, при показе — обратно. `--renderer-limit`: аргумент
`--renderer-process-limit=1` для обоих окон. Метрику «RAM ≤ 80 МБ» предлагается считать по
рабочему набору (то, что видно в диспетчере задач как занятая память): 69 МБ — выполнено.
Выделенная, но не занятая память (private) — 136 МБ. Если этого мало, остаётся вариант B
(нативный оверлей, ~10–20 МБ). Frame time игры — только PresentMon в игре (пункт 7).

## Guard и импорты exe

Исследование ожидало в exe одно подозрительное исключение (`SendInput` из tao). На деле
release-exe импортирует **10** функций из списка запрещённых. Все приходят из зависимостей,
наш код их не вызывает:

| Импорт | Откуда | Что сделано |
|---|---|---|
| `RegisterRawInputDevices`, `GetRawInputData` | tao регистрирует все мыши и клавиатуры для raw input при создании цикла событий (`event_loop.rs:200`), по умолчанию только при фокусе | **отключено**: `device_event_filter(Always)` снимает регистрацию (`RIDEV_REMOVE`); guard требует эту строку |
| `SendInput` | tao `set_focus`/fullscreen; muda — системные пункты меню Copy/Paste/… | guard запрещает эти вызовы и пункты меню |
| `SetCursorPos`, `ClipCursor` | tao API позиции и захвата курсора | guard запрещает API и права Tauri |
| `GetAsyncKeyState` | tao: один снимок клавиш, когда **наше** окно получает фокус | не опрос; описано в baseline |
| `GetKeyboardState` | tao: состояние клавиш своего потока при разборе своих сообщений | описано |
| `FindWindowExW` | tauri-runtime-wry ищет своё дочернее окно под нашим окном | описано |
| `BitBlt`, `GetDIBits` | softbuffer рисует свой буфер в своё окно; tauri конвертирует свою иконку | не захват экрана; описано |

Guard (`spikes/s1-overlay/scripts/antiban-guard.mjs`) проверяет: исходники (18 групп
правил, исключения по файлам), обязательные строки, библиотеки Windows-сборки, привязку
baseline к версиям, `package-lock.json`, права Tauri (точный белый список), манифест и
импорты exe через `dumpbin` против `antiban/imports-baseline.txt`. `cargo deny check bans`
запрещает 31 библиотеку и опасные фичи `windows`/`windows-sys`. Первая версия поймала 7 из 7
подложенных нарушений, версия после ревью — 15 из 15 (см. ниже).

## Ревью безопасности

Агент security-reviewer: **нарушений C-1…C-9, достижимых из кода, нет.** Конкурентность
(блокировка не держится во время вызовов окон, таймеры защищены номерами сессий), поток
хоткеев, Win32-вызовы и UI (нет XSS, CSP запрещает eval) — в порядке. Слабым местом был сам
guard. Сделано в спайке по итогам ревью:

| Находка | Уровень | Что сделано |
|---|---|---|
| Обход guard через строки `" //"` и `"/*"` | HIGH | правила работают по исходному тексту, пропускаются только строки-комментарии |
| Не охвачены группы API и лазейки | HIGH | +7 групп правил: запуск процессов (кроме `explorer`), `GetProcAddress`/`LoadLibrary`/`link_name`/`extern {}`/`raw-dylib`, имена и файлы игры, `GetDCEx`, `Process32Next`, `GetWindow`…, `getGamepads`/`mediaDevices`/`navigator.hid`…, `[patch]`, повышение прав; новые расширения файлов и `tauri.*.conf.json` |
| Импорт по номеру не проверялся | HIGH | импорт системных функций по ordinal — ошибка |
| Baseline не привязан к версиям | HIGH | строка `# audited:`; при обновлении tao/muda/tauri/softbuffer guard падает |
| Обязательную строку можно перекрыть | MEDIUM | `DeviceEventFilter::Never/Unfocused` и `set_device_event_filter` запрещены; при старте проверяется, что raw input не зарегистрирован (результат: 0 устройств) |
| Права Tauri — чёрный список | MEDIUM | точный белый список (2 права), запрет `remote` и `*` в окнах |
| C-8 не выполнен | MEDIUM | свой манифест `asInvoker` / `uiAccess="false"`, guard проверяет его и внутри exe |
| Старый handle окна игры | LOW | handle используется один раз и сразу сбрасывается |
| C-9: класс окна «Tauri Window» | LOW | `Mapper.Overlay`, `Mapper.Hud` |
| Стиль окна без `SWP_FRAMECHANGED` | LOW | добавлено |
| CSP/WebView2 | LOW | `object-src/base-uri/form-action 'none'`, `freezePrototype`, Permissions-Policy (gamepad, display-capture, camera, microphone, hid, usb, serial) |
| `libloading` в Cargo.lock | — | только для трея на Linux; проверка библиотек теперь по реальному дереву Windows-сборки (218 из 382) |

Проверка на подложенных нарушениях после правок: пойманы все 15, включая все обходы,
которые нашёл ревьюер.

**Перенесено в `Plan` (настоящее приложение):**
- проверка импортов собственного объектного файла Mapper (`--emit=obj`, `llvm-nm -u`):
  baseline применяется только к зависимостям, а не к нашему коду;
- разбор исходников токенизатором (acorn для JS, `syn` для Rust) вместо регулярных выражений;
- типы `OwnHwnd` / `ForeignHwnd`: handle окна игры умеет только `restore()`;
- ACL для команд (`AppManifest::commands`), HUD без команд, ограничение размеров и
  экранирование в `show_hud`/`log_line`, один поток таймеров вместо потока на таймер;
- `withGlobalTauri: false` и API в бандле; отказ на все `permission request` WebView2;
- в README честно описать, что tao на фокусе окна делает снимок всех 256 клавиш, а позиция
  курсора берётся через `GetCursorPos`;
- в релиз идёт только режим V1 (hide); V2/V3 остаются в спайке.

**Замечание к проверке.** Прогоны S-1 на стенде сделаны до этих правок. Код фокуса не
менялся, а `SWP_FRAMECHANGED` идёт с `SWP_NOACTIVATE`. S-2 после правок пройден
(30/30, медиана 25,9 мс). Фокус в обновлённой сборке подтвердит проверка в игре.

## Что меняется для `Plan`

1. **Хоткей по умолчанию — Alt+Q**, как решил автор: в PUBG свободный обзор не залипает
   (пункт 3). Переназначение на клавишу без модификатора остаётся в настройках.
2. **Выход только после отпускания всех клавиш** — обязательное поведение (уже в спайке).
3. **`device_event_filter(Always)`** — обязательная строка, guard её требует.
4. **Режим покоя V1 (hide) + low-memory + один процесс рендера.** Метрика RAM — по рабочему
   набору (≤ 80 МБ), private записывается в README.
5. **Baseline импортов из 10 строк** с обоснованием каждой — в README раздел «Почему в exe
   есть SendInput», заодно issue в tao и muda.
6. Новые правила guard: API позиции/захвата курсора, системные пункты меню muda, обязательные
   строки; права Tauri на курсор.
7. Исправление к RESEARCH.md: «одно исключение в baseline» → десять, см. таблицу выше.

## Универсальная линейка (вторая итерация спайка, 2026-10-20)

По новым требованиям (только карты рейтинга 8×8, без подгонки при каждом замере) в спайк
добавлены два хоткея: **Alt+Q** — карта приближена до упора, **Alt+W** — отдалена до упора.
У каждого свой масштаб, который настраивается один раз мастером: выбор клеток (1 — 1 км,
2 — 100 м; спрашивается всегда, после ошибки «шаг 1 км на сетке 100 м» — 10× в первой
версии) → клик на пересечение → клик на соседнее пересечение (грубый размер сразу) →
доводка колесом → Enter. Масштаб хранится по размеру оверлея (то есть по монитору).
Чужой хоткей во время замера переключает режим, свой — закрывает. Панель показывает время
бегом (спринт 6,3 м/с) и на Dacia (заглушка 120 км/ч до U-3) и сколько метров помещается на
экране (для U-2). Проверено в браузере с заглушкой API: 3 клетки по 100 м → 300 м ± 2 м,
переключение режимов сохраняет масштаб каждого; release собран, guard пройден, оба хоткея
регистрируются, raw input — 0 устройств.

**Проверка автором в игре (2026-10-20):** U-1 — масштаб совпал на разных картах 8×8 без
подгонки; U-2 — при приближении до упора 600 м помещаются; U-3 — цифр нет, скорость Dacia
будет настройкой с пометкой «не проверено».

## Что осталось проверить в игре

Пункты 1–3 пройдены, go/no-go для оверлейного режима — **GO**, можно к `Plan`. До
релиза остаются пункты 4–7 чеклиста (сетка G-1, вертикальный монитор S-4, вспышки S-2,
PresentMon S-3) и проверки миномёта G-2/G-3.
